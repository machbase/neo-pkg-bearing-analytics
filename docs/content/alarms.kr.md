#

알람은 선택한 태그를 주기적으로 판정해 상태 변화를 **이벤트**로 남기고, 설정한 채널로 알리는 기능입니다. 설정은 **설정 → 알람 설정**에 있습니다.

헤더의 알람 표시를 누르면 알람을 켜고 끌 수 있습니다. 누르는 즉시 이 값 하나만 저장되므로 앱을 다시 열어도 유지되고, 설정 탭에서 저장하지 않은 편집은 함께 저장되지 않습니다. 알람이 켜져 있으면 표시에 감시 방식 배지(**서버 상시** / **앱** / **앱 · 보기 전용**)가 함께 붙습니다. 끄면 카드의 등급은 계속 표시되지만 이벤트 기록과 알림은 멈춥니다(서버 감시 타이머도 내려갑니다. 대역 추출 타이머는 대역 추출을 따로 꺼야 내려갑니다).

> 어떤 계산으로 등급과 이벤트가 나오는지는 [이상 판정 원리]({{< relref "detection" >}})에서 다룹니다. 이 문서는 설정과 운영을 다룹니다.

## 감시 방식

먼저 판정을 **누가** 수행할지 고릅니다.

| 방식 | 판정 주체 | 앱을 닫으면 |
| :--- | :--- | :--- |
| 앱 감시 (기본) | 브라우저에 열린 앱 | 판정이 멈춥니다 |
| 서버 상시 감시 | Neo 타이머 | 계속 판정하고 이벤트를 쌓습니다 |

### 앱 감시

앱이 열려 있는 동안 판정 주기마다 선택 태그를 판정합니다. 별도 준비 없이 바로 동작하지만, 창을 닫으면 그동안의 판정은 이루어지지 않습니다.

상시 감시가 필요 없거나, 설정을 시험해 보는 단계라면 이쪽이 편합니다.

### 서버 상시 감시

**저장**하면 현재 판정 설정이 Neo 타이머로 등록되어, 앱을 닫아도 판정이 계속됩니다. 이 모드에서 앱 화면은 결과를 **표시만** 하고 판정은 서버가 담당합니다.

판정 규칙은 두 방식이 동일하므로, 모드를 바꿔도 같은 데이터에서 같은 결과가 나옵니다.

알아 둘 점:

- **설정을 바꾸면 다시 저장해야 반영됩니다.** 타이머는 저장 시점의 설정으로 동작합니다.
- **ROLLUP이 있는 테이블만 판정합니다.** 롤업이 없는 테이블의 태그는 서버 감시에서 제외됩니다. 서버 감시를 고르면 제외되는 테이블이 이 화면에 경고로 표시되며, 그런 태그는 앱 감시로 확인합니다.
- **서버 모드를 끄면 타이머가 삭제됩니다.** 패키지를 제거해도 타이머는 자동으로 지워지지 않으므로, 제거 전에 계정마다 앱에서 알람을 끕니다. 이미 제거했다면 Neo 타이머 화면에서 삭제합니다(남은 타이머는 실행할 파일이 없어 멈춘 상태입니다).
- **타이머는 저장한 계정(API 토큰의 계정) 권한으로 실행됩니다.** 다른 계정의 타이머는 목록에 보이지 않고 손댈 수도 없습니다.
- **감시할 태그가 없으면 타이머를 만들지 않습니다.**
- 타이머가 스스로 멈추면 앱이 열려 있을 때 **자동으로 다시 등록**합니다(최대 3회). 그 사이 판정이 없던 구간은 "이상 없음"이 확인된 것이 아니라는 안내가 함께 뜹니다.

### 여러 탭·PC에서 같은 계정으로 열 때

같은 계정으로 앱을 여러 곳에서 열어도 판정·알림은 **한 곳(담당)만** 맡습니다. 나머지는 결과를 표시만 하므로 알림이 겹쳐 가지 않습니다.

- **앱 감시** — 담당 탭만 판정하고 알림을 보냅니다. 나머지 탭의 헤더 배지는 **앱 · 보기 전용**으로 바뀌고, 담당이 기록한 이벤트는 목록의 30초 갱신으로 보입니다. 담당 탭을 닫으면 1분 안에 남은 탭이 이어받습니다.
- **서버 상시 감시** — 판정은 원래 서버가 하므로 달라지지 않습니다. 타이머 재등록·자동 복구 같은 뒷일만 담당 탭이 합니다.
- **설정·학습은 어느 탭에서나** 할 수 있습니다. 저장하면 다른 탭들이 10초 안에 새 설정을 읽어 반영합니다. 그 탭에서 설정을 편집하던 중이었다면 편집 내용은 그대로 두고 "다른 곳에서 설정이 저장되었습니다" 경고를 띄웁니다 — 그대로 저장하면 방금 저장된 변경을 덮어씁니다.

### 다른 계정으로 로그인이 바뀌었을 때

같은 브라우저에서 Neo 콘솔 로그인을 다른 계정으로 바꾸면, 이미 열려 있던 앱은 옛 계정 화면이라 **저장·판정·조회를 모두 멈추고** 화면 전체에 "다른 계정으로 로그인되었습니다" 안내를 띄웁니다.

- **새로고침**을 누르면 새 계정으로 다시 엽니다. 자동으로 새로고침하지는 않습니다. 이 브라우저에 새 계정의 API 토큰이 없으면 토큰 입력 화면이 먼저 뜹니다.
- 원래 계정으로 다시 로그인하면 안내가 사라지고 이어서 동작합니다.
- 옛 계정의 서버 상시 감시는 Neo 타이머라 영향 없이 계속됩니다. 앱 감시였다면 그 탭의 판정은 멈추고, 다른 PC에 옛 계정으로 열린 화면이 있으면 그쪽이 이어받습니다.

## 판정 주기와 구간

> **먼저 알아 둘 것 — 감시는 두 주기로 돕니다.**
>
> | | 하는 일 | 주기 | 설정 위치 |
> | :--- | :--- | :--- | :--- |
> | 빠른 축 | 운전/정지 · 신호 두절 · 계측 이상 · 평소 대비(베이스라인) | **판정 주기**(기본 3초) | 알람 설정 (아래) |
> | 느린 축 | **결함 패턴 — 등급과 등급 이벤트는 여기서 나옵니다** | **추출 주기**(기본 10분) | 판정 기준 → 대역 에너지 추세의 **추출 주기**, 또는 아래 알림 카드의 **주기 변경** |
>
> 아래 설정은 **빠른 축**을 정합니다. 등급이 실제로 바뀌는 것은 느린 축이라,
> 판정 주기를 1초로 줄여도 알람이 더 빨리 오지는 않습니다.
> 자세한 것은 [이상 판정 원리]({{< relref "detection" >}})에 있습니다.

알람 설정의 첫 항목은 한 문장으로 되어 있습니다.

> 직전 **[RMS 구간]** 구간의 데이터를 **[판정 주기]** 마다 판정

| 설정 | 선택지 | 뜻 |
| :--- | :--- | :--- |
| RMS 구간 | 3초 · 10초 · 30초 · 1분 · 5분 · 10분 · 30분 · 1시간 · 직접 입력(분) | 한 번 판정할 때 얼마나 긴 데이터를 볼지 (기본 10초) |
| 판정 주기 | 1초 · 3초 · 5초 · 10초 · 30초 · 1분 | 얼마나 자주 판정할지 (기본 3초) |

- 구간이 **길수록** 짧은 출렁임이 하나로 합쳐져 오경보가 줄고, 대신 반응이 느려집니다.
- 판정 주기보다 짧은 구간은 선택지에서 막힙니다. 판정 주기를 나중에 늘려 구간보다 길어지면 경고가 표시되고, 이때 판정은 구간을 판정 주기 길이로 넓혀서 하므로 빠지는 데이터는 없습니다.
- 부하가 주기적으로 변하는 설비라면 그 변동 주기보다 긴 구간을 잡으십시오. 짧으면 부하 변화가 정지·이탈로 잡힙니다.
- 태그 수가 많고 주기가 짧으면 부하 경고가 표시됩니다.

이 설정은 카드의 운전 상태(정지·신호 두절·계측 이상) 판단과 평소 대비 근거에도 같은 정의로 쓰입니다. **등급은 이 값이 아니라 추출 주기마다 결함 패턴과 ISO 존이 정합니다.**

## 알림

알람을 **언제** 낼지(확정 규칙)와 **어디로 어떻게** 보낼지(채널·심각도별 방식·재알림·묶음 발송)를 한곳에서 설정합니다.

### 언제 낼지 — 두 회차 연속

**설정이 아니라 고정 규칙입니다.** 등급은 같은 판정이 두 회차 연속이라야 확정되고, 그때 알람이 나갑니다. 나빠질 때도 좋아질 때도 같습니다.

```
회차 1   주의    관찰 이벤트 · 알림 안 감
회차 2   주의    임계 초과 · 알림 발송
회차 3   양호    (아직 복귀 아님)
회차 4   양호    정상 복귀 · 알림 발송
```

회차 간격은 **추출 주기**(기본 10분)를 따릅니다. 그 주기를 30분으로 바꾸면 확정에 60분이 걸립니다. 알림 카드 위쪽의 회차 표가 지금 설정에서 언제 알림이 가는지 보여 주고, **주기 변경** 버튼으로 바로 바꿀 수 있습니다.

감시 상태 이벤트는 빠른 축에서 시간 기준으로 판정합니다(설정으로 바꾸지 않습니다).

| 이벤트 | 조건 |
| :--- | :--- |
| 계측 이상 | 이상이 **1분** 이어지면 확정 — 스파이크 한 번에 "센서 고장"이 나가지 않게 |
| 계측 복귀 | 정상이 **5분** 이어지면 |
| 신호 두절 | 판정 주기의 6배(최소 1분) 넘게 새 데이터가 없으면. 데이터가 다시 들어오면 판정이 재개될 뿐 별도의 복귀 이벤트는 없습니다 |

### 어디로 보낼지 — 알림 채널

발송 채널은 **웹훅** 하나입니다. URL을 보고 대상 서비스를 판별해 메시지 형식을 맞춰 보내므로, 아래 서비스는 URL만 넣으면 됩니다.

| 대상 | 알아보는 URL | 메시지 형태 |
| :--- | :--- | :--- |
| Discord | `discord.com/api/webhooks/…` (`discordapp.com`도 인식) | 심각도별 색 막대가 붙은 카드 (주의 호박 · 위험 주황 · 심각 적색 · 그 외 녹색) |
| Slack | `hooks.slack.com/…` | 텍스트 3줄 (제목 · 값 · 시각) |
| Google Chat | `chat.googleapis.com/…` | 텍스트 3줄 |
| 자체 엔드포인트 (그 외 URL) | — | 제목 · 본문 텍스트 · HTML 본문 · 구조화된 이벤트 데이터 전부 |

URL을 넣고 **테스트 발송**을 누르면 실제로 한 건 보내 연결을 확인할 수 있습니다.

> **웹훅 URL은 비밀번호와 같습니다.** URL을 가진 사람은 누구나 그 채널에 게시할 수 있습니다. 유출됐다면 해당 서비스에서 웹훅을 삭제하고 새로 만드십시오 — 삭제 즉시 옛 URL은 무효가 됩니다.

이메일·문자(SMS)로 받아야 한다면 웹훅을 **자동화 도구로 중계**합니다. n8n·Node-RED·Zapier·Google Apps Script 같은 도구의 웹훅 수신 URL을 채널에 넣으면, 자체 엔드포인트용 페이로드에 메일 제목(`subject`)과 HTML 본문(`body`)까지 담겨 가므로 받은 쪽에서 바로 메일·문자로 변환할 수 있습니다.

### 알림 언어

알림 문구의 언어를 한국어 · 영어 · 일본어 중에서 고릅니다. 화면 언어와 따로 정할 수 있어, 화면은 영어로 쓰면서 현장 알림은 한국어로 받는 식으로도 쓸 수 있습니다.

- 처음에는 지금 화면 언어가 선택되어 보입니다. 서버 상시 감시의 알림에 적용하려면 **저장**해야 합니다. 한 번도 저장하지 않은 계정은 예전처럼 한국어로 보냅니다.
- 제목(등급 · 유형), 값 줄, 이벤트 사유가 모두 그 언어로 나갑니다. 설비 별칭 · 태그명은 입력한 그대로입니다.
- **테스트 발송**은 저장하지 않아도 지금 고른 언어로 보내므로, 저장하기 전에 문구를 확인할 수 있습니다.

### 심각도별 알림

심각도마다 알림 여부와, 비정상이 이어질 때 다시 알릴 주기를 정합니다.

| 열 | 선택지 | 뜻 |
| :--- | :--- | :--- |
| 알림 방식 | 즉시 · 알림 안 함 | 이 등급의 이벤트를 보낼지 |
| 지속 시 재알림 | 끔 · 30분 · 1시간 · 2시간 · 6시간 | 비정상 상태가 계속될 때 다시 알릴 주기 |

표에는 등급 세 줄 아래에 **감시 이상** 한 줄이 더 있습니다.

| 행 | 무엇 | 알림 방식 기본값 | 재알림 기본값 |
| :--- | :--- | :--- | :--- |
| 주의 | 결함 패턴이 잡힘(진폭은 아직 낮음) | 즉시 | 2시간 |
| 위험 | 결함 패턴 + ISO 위험 존 | 즉시 | 1시간 |
| 심각 | 결함 패턴 + ISO 심각 존 | 즉시 | 30분 |
| **감시 이상** | 신호 두절 · 계측 이상 · 계측 복귀 | 즉시 | 없음(`—`) |

**기본값은 네 줄 모두 즉시입니다.**

- **'주의'도 기본으로 켜져 있습니다.** 이 앱에서 주의는 "결함 패턴이 잡혔다"는 뜻이라, 끄면 이 도구가 잡는 것의 대부분이 알림 없이 목록에만 쌓입니다.
- **재알림이 기본으로 켜져 있습니다.** 확정 뒤 침묵하면 "아까 그거 단발이었나"를 알 수 없기 때문입니다. 정상 설비는 확정 자체가 드물어 재알림으로 늘어나는 양이 거의 없고, 쌓이는 것은 진짜 결함이 이어질 때뿐입니다.
- **감시 이상은 설비 등급이 아닙니다** — "이 설비가 얼마나 나쁜가"가 아니라 "**이 값을 믿을 수 있는가**"입니다. 그래서 등급 라우팅과 따로 켜고 끕니다. 감시가 눈을 감았는데 아무도 모르는 상태가 가장 나쁜 실패이기 때문입니다.
- 감시 이상 행에는 재알림이 없습니다. 두절·계측 이상은 **상태가 유지되는 동안 이벤트 자체가 안 나므로** 다시 알릴 대상이 없습니다.
- **알림 안 함**이어도 이벤트는 기록됩니다 — 발송만 건너뜁니다. 재알림 이벤트도 마찬가지로 이력에는 항상 남습니다.
- **복귀 알림**은 주의·위험·심각 중 하나라도 즉시로 되어 있으면 발송됩니다. 알람을 받았다면 해제도 알아야 하기 때문입니다.
- 채널은 켜져 있는데 **등급 세 줄(주의·위험·심각)** 이 모두 알림 안 함이면 화면에 경고가 표시됩니다(감시 이상 행은 세지 않습니다).

### 한꺼번에 많이 날 때 — 묶음 발송

같은 판정 회차에 **같은 유형·같은 등급의 이벤트가 5건 이상이면 한 건으로 묶어** 보냅니다.

```
[주의] 신호 두절 91대
PUMP_A 38 · FAN_B 25 · LINE_3 16 · 외 12
6분 무수신
2026-10-12 14:03:20
```

수집이 끊기면 전 태그가 같은 회차에 두절을 냅니다. 하나씩 보내면 채널 한도(Slack 초당 1건 · Discord 2초 5건)에 걸려 **임의의 일부만 도착**하는데, "91대 두절"이 "무작위 8대 두절"로 도착하면 나머지는 멀쩡한 줄 알게 되므로 전부 안 오는 것보다 나쁩니다.

4건 이하는 개별로 보냅니다 — 설비 두세 대는 태그·값·기준까지 보이는 쪽이 쓸모 있습니다.

**이력은 항상 개별로 저장됩니다.** 묶음은 발송 형태일 뿐이라 이벤트 목록·CSV는 그대로입니다.

## 웹훅 설정 가이드

### Discord

서버 관리 권한이 있는 채널에서 진행합니다. 알람 전용 채널(예: `#진동-알람`)을 하나 만들어 거는 것을 권합니다 — 대화 채널에 섞이면 알람을 되짚기 어렵습니다.

1. 채널 옆 **⚙️ 채널 편집** 클릭
2. 왼쪽 메뉴 **연동** (Integrations)
3. **웹후크 → 새 웹후크** — 이름·아바타는 자유 (예: `진동 감시`)
4. **웹후크 URL 복사**

URL은 `https://discord.com/api/webhooks/…` 형태입니다. 앱의 웹훅 칸에 붙여넣고 테스트 발송으로 확인합니다.

알림은 심각도 색 막대가 붙은 카드로 도착합니다. 발송 제한은 웹훅당 2초에 5건 수준으로, 정상 운영에서는 닿지 않습니다.

### Google Chat (스페이스)

**Workspace(회사·조직) 계정 전용**입니다 — 개인 `@gmail.com` 계정의 Chat에는 웹훅 메뉴가 없습니다. 웹훅은 스페이스에만 달 수 있습니다 (DM 불가).

1. [chat.google.com](https://chat.google.com) → **스페이스 → + 스페이스 만들기** (예: `진동-알람`)
2. 스페이스 이름 클릭 → **앱 및 통합** (Apps & integrations)
3. **웹훅 → 웹훅 추가** — 이름 입력 (예: `진동 감시`), 아바타 URL은 비워도 됨 → **저장**
4. 생성된 **URL 복사**

URL은 `https://chat.googleapis.com/v1/spaces/…` 형태입니다. 발송 제한은 스페이스당 분당 60건입니다.

웹훅 메뉴가 안 보이면 개인 계정이거나, Workspace 관리자가 웹훅을 꺼 둔 경우입니다 (관리 콘솔 → Chat 설정에서 허용 필요).

### Slack

Slack은 웹훅이 "앱" 안에 들어 있어 앱을 하나 만들어야 합니다. 5분 정도 걸립니다.

**1) 앱 만들기 — [api.slack.com/apps](https://api.slack.com/apps)**

1. 워크스페이스 계정으로 로그인 → **Create New App**
2. **From scratch** 선택
3. 앱 이름 입력 (예: `진동 감시`) → 붙일 **워크스페이스 선택** → **Create App**

**2) Incoming Webhooks 켜기**

여기서부터는 방금 만든 **앱의 설정 화면 안**입니다. [api.slack.com/apps](https://api.slack.com/apps)는 앱 목록 페이지라 메뉴가 없으니, 목록에서 앱 이름을 클릭해 들어갑니다.

1. 왼쪽 사이드바 **Features → Incoming Webhooks** (안 보이면 **Basic Information** 페이지의 "Add features and functionality" 아코디언을 펼치면 같은 화면으로 가는 카드가 있습니다)
2. 토글을 **On**으로
3. 아래쪽 **Add New Webhook to Workspace** 클릭
4. 알람 받을 **채널 선택** (예: `#진동-알람`) → **허용**
5. 생성된 **Webhook URL 복사**

URL은 `https://hooks.slack.com/services/T…/B…/…` 형태입니다.

**우회로** — 앱을 만들지 않으려면: Slack 클라이언트에서 워크스페이스 이름 → **도구 및 설정 → 앱 관리** → 검색창에 **"Incoming WebHooks"** → **Slack에 추가** → 채널 선택. Slack이 레거시로 표시하지만 동작은 같습니다.

알아 둘 점:

- 발송 제한은 **초당 1건** 기준으로, 이 문서의 서비스 중 가장 빡빡합니다.
- 무료 플랜은 **90일 지난 메시지가 숨겨집니다.** 알람 이력은 Slack이 아니라 앱의 이벤트 목록에서 되짚으십시오 — 이벤트는 자동 삭제되지 않습니다.
- 채널을 여러 개 쓰려면 **Add New Webhook to Workspace**를 반복하면 채널마다 별도 URL이 나옵니다. 단, 앱의 웹훅 칸은 하나이므로 심각도별로 다른 채널에 보내는 것은 지원하지 않습니다.

## 대역 에너지 근거 (선택)

전체 진동은 거의 안 움직이는데 특정 주파수 대역만 뛰는 변화 — 대표적으로 초기 베어링 결함 — 를 근거로 보려면 대역 추출을 켭니다. **설정 → 판정 기준 → 대역 에너지 추세**에 있습니다.

사용 순서는 다음과 같습니다.

1. **대역·결함 패턴 추출** 스위치를 켜고 추출 주기를 정합니다 (10분 · 30분 · 1시간).
2. 표본이 부족하면 **과거 데이터 채우기**로 이미 DB에 있는 원시 데이터를 소급 계산합니다.
3. 표본이 충분해지면 **학습**으로 계열별 정상 기준을 만듭니다.
4. 학습된 계열이 한계를 넘으면 카드(숫자에 마우스)와 근거표에 **한계 대비 배수**로 표시됩니다.

> **대역은 알림을 내지 않습니다.** 여러 계열 중 하나만 넘어도 켜지는 구조라 오탐이 많고, 판정 시간축도 등급과 다릅니다.
> 대역 값은 알림이 아니라 **"어느 대역이 움직였나"로 원인을 좁히는 근거**로 씁니다.
> 같은 이유로 베이스라인 이탈도 알림을 내지 않습니다 — 표시만 됩니다.

주파수 대역 8개에 더해 **포락선 계열**(주기성, 베어링 품번이 있으면 BPFO·BPFI·BSF 결함주파수)도 함께 쌓이고 같은 방식으로 학습됩니다. 각 태그 줄의 `4/9 계열 학습됨`에서 분모는 그 태그에서 **측정 가능한 계열 수**입니다 — 샘플레이트나 마운팅 상한이 낮으면 상위 대역이 빠지고, 베어링 품번이 없으면 결함주파수 계열이 빠지며, 이는 정상입니다. 자세한 설정은 [첫 설정 › 대역·결함 패턴 추출]({{< relref "first-setup#대역결함-패턴-추출" >}})에 있습니다.

> 학습은 **정상 운전이 확실할 때** 하십시오. 결함이 이미 진행 중이면 그 결함이 정상 기준이 됩니다.

## 이벤트

판정 결과는 Neo에 이벤트로 쌓이며, 앱을 다시 열거나 타이머가 다시 돌아도 이어집니다.

이벤트는 **모니터링** 탭 아래쪽 목록에서 확인합니다. 기간 칩과 태그·유형 필터로 좁혀 볼 수 있고, 각 행을 누르면 그 시점의 상세분석으로 이동합니다. 목록 칸의 뜻은 [사용 방법 › 이벤트 목록]({{< relref "usage#이벤트-목록" >}})에, 유형별 의미와 기록 규칙은 [이상 판정 원리 › 이벤트]({{< relref "detection#이벤트" >}})에 있습니다.

- 목록은 30초마다 새로 읽습니다. 서버 상시 감시가 기록한 이벤트도 새로고침 없이 나타납니다.
- 목록과 건수는 **지금 감시 중인 태그**만 셉니다. 데이터 소스에서 선택을 해제한 테이블의 이벤트는 빠지지만 지워지지는 않습니다.
- 태그·유형 필터는 조회 조건입니다 — 필터에 맞는 이벤트 중 최근 **200건**을 표시하고, 건수는 필터에 맞는 전체입니다. 헤더의 **최근 이벤트** 칸은 필터와 무관합니다.
- 전체 이력은 **저장**(내보내기)에서 기간을 지정해 CSV·JSON으로 받습니다. 선택을 해제한 테이블의 이벤트도 포함됩니다.
- 이벤트는 자동으로 삭제되지 않습니다. 철거한 설비의 이력은 **설정 → 데이터 관리 → 태그별 정리**에서 지웁니다.

## 감시 상태 확인

"이벤트가 없다"에는 두 가지 뜻이 있습니다 — 설비가 정상이거나, 감시가 돌지 않거나. 앱은 이 둘을 구분해 모니터링 화면 맨 위에 알립니다.

**서버 감시**

| 표시 | 뜻 | 조치 |
| :--- | :--- | :--- |
| 서버 감시 타이머가 등록되어 있지 않습니다 | 서버 감시가 등록되지 않음 | **다시 등록** 버튼 |
| 서버 감시가 멈춰 있습니다 | 타이머가 정지 상태 (사유 함께 표시) | **다시 등록** 버튼(앱이 열려 있으면 자동으로 최대 3회 재등록) |
| 마지막 판정이 N분 전입니다 | 타이머는 돌지만 판정이 멈춤 | **다시 등록** 버튼 |
| 서버 감시가 N 전 멈췄다가 자동으로 복구됐습니다 | 자동 재등록으로 살아남. 그 사이 구간의 "이상 없음"은 확인된 것이 아님 | 필요하면 그 구간을 상세분석으로 확인 |
| … 자동 복구 N회로 살아나지 않았습니다 | 재등록해도 계속 멈춤 | 함께 표시된 사유 확인 |
| 감시 타이머 상태를 확인할 수 없습니다 | Neo 타이머 목록을 읽지 못함 | Neo 연결 확인 |
| 판정 대상이 0개입니다 | 감시 태그에 새 데이터가 없음 | 데이터 수집 상태 확인 |
| N대를 훑었지만 결함 패턴을 잰 태그가 0입니다 | 등급을 켜는 축이 비어 알람이 날 수 없음 — 회전수·베어링이 없거나 판정 창에 표본이 모자람 | **설비 정보 열기** → RPM·베어링 입력 |
| 서버 감시 1회차가 N초 걸립니다 | 회차가 주기에 가깝거나 넘어 일부 주기를 건너뜀 | **설정 열기** → 판정 주기를 늘리거나 감시 태그를 줄임 |
| 서버 감시가 알림 설정을 읽지 못해 이벤트 N건을 알리지 못했습니다 | 발송할 때 계정의 알림 설정을 읽지 못함. 이벤트 기록은 남아 있음 | **알림 설정 열기** → 알림 설정을 다시 저장 |
| 직전 판정 상태를 읽지 못해 회차를 건너뛰었습니다 | 판정 상태를 모르는 채 판정하면 알림이 중복되므로 그 회차를 판정하지 않음 | DB 연결 확인. 다음 회차에 자동으로 다시 시도 |
| 태그 N개 처리 실패 | 그 태그만 판정·저장하지 못함(나머지는 정상 처리). 사유 함께 표시 | 사유 확인. 다음 회차에 자동으로 다시 시도 |
| 회차가 오류로 끝났습니다 | 회차 전체가 오류로 끝남. 사유 함께 표시 | 사유 확인. 다음 회차에 자동으로 다시 시도 |

**대역 추출**

| 표시 | 뜻 | 조치 |
| :--- | :--- | :--- |
| 대역 추출 타이머가 등록되어 있지 않습니다 / 대역 추출이 멈춰 있습니다 | 대역 추출 타이머가 없거나 정지 | **다시 등록** 버튼 |
| 대역 추출이 N 동안 회차를 마치지 못했습니다 | 타이머는 실행 중인데 회차 기록이 추출 주기의 3배(최소 30분) 넘게 멈춤 | 자동으로 다시 등록. 계속되면 사유 확인 |
| 대역 추출이 켜져 있지만 조건을 갖춘 태그가 없어 돌지 않습니다 | RPM(과 샘플레이트 정보)을 갖춘 태그가 없음. 사유 함께 표시 | 설비 정보에서 RPM 입력 |

**앱 공통**

| 표시 | 뜻 | 조치 |
| :--- | :--- | :--- |
| 앱 판정이 N 동안 멈춰 있습니다 | 앱 감시에서 브라우저가 판정을 지연(백그라운드 탭 등) | 탭을 다시 열거나 새로고침 |
| N대 중 M대가 결함 패턴을 못 재 등급이 서지 않습니다 | RPM이나 베어링 형식이 없는 태그가 있음 | 설비 정보 입력 |
| 태그 N개가 표시 상한(테이블당 60개 · 전체 100개)에 걸려 … | 상한 밖 태그는 감시에서 빠짐 | 데이터 소스에서 범위 좁히기 |
| 데이터를 다시 불러오지 못했습니다 | 설정 저장 뒤 등 데이터를 다시 읽다가 테이블 조회가 실패함. 마지막으로 불러온 데이터로 감시를 이어 가며 자동으로 다시 시도합니다(10초부터 최대 5분 간격). 새로 고른 테이블은 성공할 때까지 감시되지 않습니다 | 대개 기다리면 풀립니다. **지금 다시 시도** 버튼. 계속 실패하면 그 테이블이 지워졌거나 권한이 없는지 확인하고, 필요하면 설정에서 선택을 해제 |

등급이 짧은 간격으로 악화를 반복하면(최근 2시간에 임계 초과 3회 이상) 카드에 **등급 반복 N회** 배지가 붙습니다. 결함 근거가 채택 기준선 근처에서 오가는 상태로, 부하 변동 때문일 수도 있고 결함 초기일 수도 있습니다. 배지를 누르면 마지막 악화 시점의 상세분석이 열립니다 — 설정으로 가리지 말고 결함 근거와 포락선 스펙트럼으로 원인을 확인하십시오.

## 확인 순서

알람이 의도대로 도는지 볼 때는 이 순서로 확인합니다.

1. 헤더 알람 표시가 **켜짐**인지, 서버 모드라면 배지가 붙어 있는지.
2. 화면 상단에 감시 상태 경고가 없는지.
3. **모니터링 → 이벤트** 목록에 판정 결과가 쌓이는지. 유형·태그 필터로 좁혀 봅니다.
4. 알림이 안 오면 채널 **테스트 발송**으로 발송 경로를 먼저 분리해 확인합니다.
5. 테스트는 오는데 실제 알람이 안 오면 **심각도별 알림 방식**을 확인합니다. 그리고 등급은 **두 회차 연속**이라야 확정되므로, 한 회차만 뜬 건은 `관찰`로만 남고 알림이 안 갑니다.
6. 서버 모드에서 특정 태그만 조용하면 그 테이블에 ROLLUP이 있는지 확인합니다.
7. 진동은 분명히 높은데 아무 알람도 없으면 **회전수와 베어링 품번**이 채워져 있는지 확인합니다 — 둘 중 하나가 비면 결함 패턴을 계산할 수 없어 등급이 오르지 않고, 카드에 **판정 보류**(판정 못 함)로 나타납니다.
